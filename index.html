03 / CASE STUDIES

技术难题如何被解决。

从问题到方案，再到验证。以下是根据个人项目履历与公开技术文档整理的具体实践。

01 / GODOT · ARCHITECTURE

《过早》：UI 与业务逻辑解耦

问题

经营界面、弹窗遮罩与交互输入混杂；出餐和结算业务依赖 UI，影响测试与维护。

方案

五段经营状态机；按界面层级设计输入路由；用状态快照投影与信号同步只读 UI，结算下沉至独立服务。

验证

通过分支评审、JSON 配置校验和 43 组场景化测试覆盖经营主流程及异常输入。

INPUT → STATE MACHINE → SERVICE → READ-ONLY VIEW → TEST
02 / UNITY · SYSTEM DESIGN

SLG+RTT：调度、寻路与热重载

问题

并行 Tick 存在 Unity API 跨线程调用风险；多单位寻路成本不可控；配置变更依赖重编译。

方案

按依赖分组在主线程执行 Tick；八向加权 A* 与寻路排队；热重载与快照差异比较。

边界

增加超时与追帧上限，处理 Domain Reload 状态恢复，并通过并发队列将异步物流结果回传主线程。

SCHEDULE → DEPENDENCIES → MAIN THREAD → TRACE
03 / GODOT · GAMEPLAY

《芽》：围绕生长与枯萎构建平台解谜

设计目标

让植物的成长与枯萎成为主动的路线选择：小形态通过狭缝，其他形态完成不同的移动与藤蔓交互，毒雾和机关引导玩家规划路径。

程序实现

使用单一角色节点配合形态资源驱动移动参数、能力与视觉；在切换时深拷贝运行时资源，避免共享配置被意外写入。

限时开发方法

把关卡事件约束在局部总线内，避免跨关卡串扰；利用 JSON 白盒地形与实体生成降低搭建和测试成本。

GROW / WITHER → FORM ABILITIES → ROUTE PUZZLES → SCENE TEST

05 / HOW I WORK

一个循环，
从想法到验证。

好的设计需要被实现，好的实现需要被玩家感知。我倾向于把文档、代码、素材和测试放在同一条可追踪的迭代链条中。

  1. 01
    定义体验目标玩家应该如何判断、行动、得到反馈。
  2. 02
    把规则转为契约条件、时序、边界、数据与失败路径。
  3. 03
    构建可玩切片代码、资产、UI 与声音共同形成可操作体验。
  4. 04
    测试并留下证据日志、场景测试、回归检查与真实试玩共同收敛设计。
