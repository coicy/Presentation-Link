03 / CASE STUDIES

真正的技术含量，
藏在困难的取舍里。

不只罗列技术名词，而是把复杂性拆开：问题从哪里来，为什么不选看似简单的方案，最终由哪个模块负责，以及怎样确认结果符合设计意图。

01 / GODOT · ARCHITECTURE

《过早》｜让经营规则摆脱 UI 的束缚

问题

当经营流程、遮罩、弹窗与业务计算相互牵连，一次 UI 改动就可能影响出餐、收入和玩家操作。

方案

通过五阶段流程状态机、分层输入路由、只读运行时投影及信号通知，建立业务系统与表现层的边界；判定和结算进入独立服务。

验证

使用 JSON 配置和资产校验辅助回归，通过分支评审与履历记载的 43 组场景化测试检查正常流程与异常输入。

INPUT → STATE MACHINE → SERVICE → READ-ONLY VIEW → TEST
02 / UNITY · SYSTEM DESIGN

SLG+RTT｜为复杂模拟建立确定的时序

问题

多处理器 Tick、单位寻路、物流任务和配置变化同时发生；不当的并行策略会引入 Unity API 跨线程风险和状态先后不一致。

方案

主线程执行按依赖划分的 Tick 组；八向加权 A* 与请求排队控制寻路开销；配置快照差异支持热重载和版本演进。

边界

加入处理器超时、追帧上限与 Domain Reload 状态恢复，经由并发队列把异步任务结果带回主线程；尚无公开性能基准。

SCHEDULE → DEPENDENCIES → MAIN THREAD → TRACE
03 / GODOT · GAMEPLAY

《芽》｜用三种形态重塑空间解法

设计目标

生长与枯萎不仅改变角色属性，更让玩家主动改变形态以穿越地形、寻找机关与规划路线。

程序实现

单角色节点共享基础移动，运行时形态资源决定能力和视觉差异；通过副本隔离避免共享资源被意外写入。

限时开发方法

关卡局部事件控制生命周期；JSON 白盒缩短搭建与回归路径，为形态和路线可达性提供验证入口。

GROW / WITHER → FORM ABILITIES → ROUTE PUZZLES → SCENE TEST

04 / ART · PIPELINE

《过早》｜把 AI 概念图变成游戏可用资产

输入

完整的视觉概念不等于可交互界面：切分颗粒度、按钮状态、透明边缘、资源命名和引擎布局都可能成为阻碍。

制作

按交互结构分解视觉需求，AI 辅助生成概念和 UI 参考，拆分图像、整理命名与格式，再依据游戏规格整合。

集成

通过编辑器登记和校验，在真实场景中检查裁切、层级、焦点、状态反馈与画面一致性。

BRIEF → CONCEPT → CUT / FORMAT → IMPORT → VISUAL QA

05 / HOW I WORK

不止交付功能。
交付可解释的系统。

设计确定目标，架构确定边界，代码实现规则，视觉传递反馈，测试提供证据。我追求这些环节可以被连接、追踪、维护，而不只是各自看起来完成。

  1. 01
    定义体验目标玩家应该如何判断、行动、得到反馈。
  2. 02
    把规则转为契约条件、时序、边界、数据与失败路径。
  3. 03
    构建可玩切片代码、资产、UI 与声音共同形成可操作体验。
  4. 04
    测试并留下证据日志、场景测试、回归检查与真实试玩共同收敛设计。
