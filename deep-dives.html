01 / DEEP DIVEGODOT 4 / GAMEPLAY ENGINEERING / GAME JAM → ITERATION

《芽》｜把生长与枯萎设计成一套空间规则

三种植物形态不是三套独立人物控制器，而是同一个角色在资源、碰撞、能力和环境约束下呈现的不同解题状态。形态系统必须能够支持玩家决策，而非只改变角色外观。

主程序、策划；48 小时团队原型与后续同项目工程资料原始参赛机制与后续仓库版本分开说明
Godot 4GDScriptResourceFinite State MachineLevel Prototyping
01

背景、目标与约束

01 · 体验目标

成长与枯萎需要是主动决策，而非单纯的升级或受罚；玩家要观察狭缝、藤蔓、机关与毒区，再决定是否改变形态。

02 · 约束条件

不同形态必须共用角色的基础移动、场景生命周期和输入接口；限时开发不能为每种形态维护一整份 Player 场景。

03 · 技术策略

保留单个 CharacterBody2D 角色节点，通过 FormDefinition 等资源描述可用能力和移动参数；形态变化时将能力差异传播到移动、视觉与交互模块。

04 · 风险与取舍

把所有逻辑塞进统一状态机容易造成臃肿；复制三套控制器又会导致动画、碰撞和关卡逻辑持续分叉。因此让状态机只管理状态转换，能力执行和移动分别管理。

02

核心架构决策与工程权衡

01

01 · 形态资源是配置，不是共享运行时状态

具体问题

Godot Resource 会被多个实例引用；直接修改配置可能让一次角色切换影响后续创建的角色或场景。

采用的处理方式

配置资源保持只读，进入新形态时生成运行时副本；由 FormController 持有当前形态，能力与视觉只消费更新后的状态。

取舍与边界：这是一种所有权控制策略，不能仅凭代码结构宣称已经消除所有切换异常。

02

02 · 形态切换要同时处理空间与能力

具体问题

角色体型变化不仅影响贴图，也会影响碰撞、移动参数及正处于执行中的能力。

采用的处理方式

先校验目标形态与空间条件，再更新资源和碰撞轮廓，并通知 Visuals / AbilityController / HUD；切换时清理原形态留下的持续状态。

取舍与边界：具体角色手感仍要以物理场景和玩家操作测试为准。

03

03 · 局部事件总线限定关卡生命周期

具体问题

用全局事件广播所有关卡操作容易导致上一个场景留下订阅者，造成重复触发与跨关串扰。

采用的处理方式

将局部机关、关卡目标和交互状态放在当前关卡事件域中；全局只保留少量跨场景生命周期事件。

取舍与边界：降低全局耦合不代表完全不需要场景装配检查。

04

04 · JSON 白盒服务于验证，而不是替代设计

具体问题

48 小时内手工搭建、修改、重新进场验证成本过高，容易把时间消耗在场景编辑操作。

采用的处理方式

以 JSON 描述白盒地形和实体，快速重建路线；验证形态能力是否能够到达机关、通过限制通道及触发必要交互。

取舍与边界：白盒通过不代表最终视觉引导、动效或关卡节奏已经验证。

02 / DEEP DIVEGODOT 4 / MANAGEMENT GAME / SOFTWARE ARCHITECTURE

《过早》｜将经营业务从 UI 的复杂性中解放出来

一款经营游戏的难点并不只是订单数量，而是大量状态、输入和反馈能够同时成立。将界面从业务权威的位置移开，才能让结算、交互和资产调整进入可验证的迭代循环。

主程序、策划与资产流程；多人协作（据个人项目履历）项目源码已在 GitHub（项目方确认）；链接与测试证据待核对

01

背景、目标与约束

01 · 业务目标

把从接单到出餐、雇佣与经营反馈组织成可理解的经营循环，使玩家知道当前可以做什么、为什么成功或失败。

02 · 架构约束

UI 不应该直接计算营业收入，也不应该持有完整业务状态；多个覆盖层与弹窗必须能够明确决定输入的归属。

03 · 解决路径

五个经营流程状态由业务状态机管理；UI 订阅运行时只读快照，变化由信号通知；判定和经济计算下沉到独立服务。

04 · 可验证性

通过配置驱动和 43 组场景化测试覆盖经营流程与异常输入；数字是个人项目履历中的测试用例记录，尚无公开 CI 报告。

02

工程决策与取舍

01

01 · UI 是展示层，不是规则权威

具体问题

当多个按钮直接修改订单、顾客与库存时，同一规则会散落在界面回调中，改版后容易产生不同入口的不一致。

采用的处理方式

业务模块管理状态及转移，输出运行时快照投影；UI 只消费投影与信号，负责反馈和意图提交，不拥有独立结算事实。

取舍与边界：快照需要明确生成时机和刷新顺序，不能把延迟刷新的视觉现象误认为业务已完成。

02

02 · 输入路由处理遮罩与游戏操作冲突

具体问题

弹窗覆盖游戏画面后，点击本应只触发弹窗，却可能透传到底层经营操作。

采用的处理方式

根据 UI 层级、遮罩和焦点建立输入优先级策略，让最高可交互层先处理事件，再决定是否继续分发。

取舍与边界：触屏、键鼠与不同 UI 层级仍需要分别验证。

03

03 · 出餐判定和经济结算独立于画面

具体问题

如果成功判定和金钱变化依赖 UI 节点存在，难以编写无界面的异常场景测试，也会产生重复提交风险。

采用的处理方式

将业务输入转换为可测试的服务调用，由服务计算出餐条件与经济结果，再更新运行时状态并向 UI 发出变化通知。

取舍与边界：需要特别审查同一事件被重复触发、场景切换和保存恢复等边界。

04

04 · 配置与素材走统一登记入口

具体问题

数值表和 UI 图片直接散落于场景会使重新命名、移动文件或修订资源变得困难。

采用的处理方式

将数值统一纳入 JSON 配置，配套编辑器插件登记、校验资产，形成从生成/整理到导入和引用的流程。

取舍与边界：内容管线的目标是减少手工错误；不虚构尚未量化的节省时间和性能提升。

03 / DEEP DIVEUNITY / C# / REAL-TIME SYSTEMS / WORK IN PROGRESS

SLG × RTT｜为实时生产、物流和战斗建立系统秩序

建造、生产、物流与军团控制并存时，工程问题会从单个功能升级为时序、依赖、路径搜索和线程所有权。这里讨论如何约束这些复杂度，而不是凭空宣称性能突破。

独立在研项目；技术架构、玩法系统与编辑器工具（据个人项目履历）在研 / 暂不公开源代码与实机演示
UnityC#Tick SchedulingA*Data Hot ReloadAsync Queue
01

背景、目标与约束

01 · 体验与系统目标

将建造生产、资源运输与即时战术部队调度连接成一个策略循环，而非互不相干的功能菜单。

02 · 系统约束

模拟器中存在需要排序的 Tick 处理器，Unity 的大部分对象 API 必须在主线程调用；同时存在大量独立的寻路和物流请求。

03 · 关键决定

把 Tick 划为独立组、依赖组、收尾组并收敛至主线程执行；将适合异步工作的物流计算与主线程状态提交分开。

04 · 验证边界

目前只能根据个人项目履历说明工程设计与实现记录，没有公开 profiler、规模基准或对照测试，不作帧率与吞吐承诺。

02

工程决策与取舍

01

01 · “并行”不是无条件性能优化

具体问题

处理器并发执行可能跨线程访问 Unity API，或把生产、库存扣减与结算顺序打乱。

采用的处理方式

按处理器优先级和依赖关系分组，把 Unity 对象访问限定在主线程；对执行时间、追帧和单个处理器设定限制。

取舍与边界：主线程调度仍可能出现帧预算压力，需要持续分离纯数据计算与主线程提交。

02

02 · 八向加权 A* 尊重地形和对角成本

具体问题

单位数量增长后，重复寻路难以控制；若对角移动按直线成本估计，会导致不合理路径选择。

采用的处理方式

支持八方向邻接、对角代价修正和地形通行权重；对请求排队并预估路程时间，与既有使用 Dijkstra 的信使逻辑通过接口隔离。

取舍与边界：不同用途的寻路行为不应被统一替换，尤其是已经依赖原算法语义的运输系统。

03

03 · 配置热重载需要差异追踪

具体问题

数值迭代完全依赖重编译降低了策划与开发协作效率，运行时还存在资源版本切换问题。

采用的处理方式

读取新旧配置快照，区分新增、修改、删除；考虑配置版本迁移以及 Domain Reload 后如何恢复关联状态。

取舍与边界：热重载时要识别哪些数据允许替换，哪些是已经产生的运行中状态，避免覆盖玩家当前进度。

04

04 · 异步任务只返回结果，不直接修改场景

具体问题

批量物资转移若完全在主线程串行处理，容易造成阻塞；若子线程直接操作场景对象又存在线程安全风险。

采用的处理方式

使用任务队列与线程池承接可分离的计算任务，再通过并发队列把完成事件送回主线程统一提交。

取舍与边界：并发结果需要明确过期判定、任务取消及场景生命周期，不把异步回调当成原子事务。

03

关键流程及其验证边界

构建 / 生产请求→Tick 分组调度→寻路 / 物流任务→主线程结果提交→资源与队列更新→日志 / 回归验证

04 / DEEP DIVEART DIRECTION / AI-ASSISTED PRODUCTION / IN-ENGINE INTEGRATION

视觉资产工程｜跨越 AI 概念、交互规格与游戏运行时

一张漂亮的生成图不是最终资产。真正的制作任务是把视觉构想转化为可切分、可复用、可交互、可验收的游戏资源，同时保留明确的来源和责任边界。

《过早》美术资源生成与集成、与美术沟通的制作流程过程说明 / 未公开全部原始素材

01

背景、目标与约束

01 · 实际需求

根据经营交互定义按钮、图标、装饰、背景、反馈状态以及视图切换所需的资产，而不只是生成一整张展示效果图。

02 · 素材问题

模型生成的整张界面图可能把可交互元素、阴影和背景融合在一起，导致无法独立切换状态或缩放。

03 · 制作策略

先确认规格与风格，再生成概念图和界面图；以可复用的 UI 元素为单位进行切分、命名、导入、适配与验收。

04 · 交付边界

并非所有视觉资产均具有可独立编辑的图层源文件；实际在游戏中使用前还需核对素材许可、裁切和显示效果。

02

工程决策与取舍

01

01 · 在生成提示词之前定义资源合同

具体问题

不明确尺寸、比例、交互状态和目标平台，容易得到无法按需求切分的插画式 UI。

采用的处理方式

先将交互流程拆成资源清单，说明哪些是静态装饰、哪些需要 Hover/Pressed/Disabled 等状态，以及容器的空间限制。

取舍与边界：这是一套实践方法，不声称已有完整自动化生产线。

02

02 · 先审查整图，再决定拆分策略

具体问题

文本、光影与按钮装饰常互相覆盖，强行按矩形切图可能留下背景污染或接缝。

采用的处理方式

人工检查构图和可分离性，必要时针对元素二次生成，再按游戏侧结构分割为独立资源。

取舍与边界：应保留素材修改与来源记录，不能把二次处理后的图片当作人工原创原画。

03

03 · 引擎里的实际状态决定最终质量

具体问题

资源在生成预览中正确，导入后可能出现锚点、拉伸、透明边缘、点击区域或层级问题。

采用的处理方式

导入 Godot 后按真实 UI 容器验证尺寸与裁切，检查菜单遮罩、点击反馈和交互状态之间的一致性。

取舍与边界：通过一次静态截图不能替代对交互状态和多窗口尺寸的验证。

04

04 · 用资产登记缩小沟通和回归成本

具体问题

多人协作中，不同命名习惯和资源路径变化会让 UI 调整产生隐蔽的引用错误。

采用的处理方式

配合编辑器资产登记与校验，形成资源名、用途、路径及复用位置的约定，并让美术与程序围绕同一条清单讨论。

取舍与边界：如无可公开记录，不编造资产数量、工时节约率或风格一致性的量化指标。

03

关键流程及其验证边界

交互需求→资源规格→AI 概念 / 界面参考→元素分割→引擎导入→状态 / 尺寸 / 许可验收

信息依据

个人项目陈述中明确负责《过早》大部分美术资产生成、概念/界面图拆分和游戏实现。这里展示工作方法和技术约束，不公开未授权的原素材。

《过早》项目代码已在 GitHub（项目方确认）；资产相关的实际实现位置及公开权限待核对。

不能直接推断

素材生成与最终资产设计的权利边界、可编辑源文件和许可信息需要逐项核验。

02

工程决策与取舍

01

01 · 先定义客观 AC，再允许实现

具体问题

缺少客观验收标准时，任务结束只代表代码有变化，不代表玩法要求已经满足。

采用的处理方式

设计、架构与验收标准分阶段冻结，在实现之前形成能逐项判断通过/失败的 AC。

取舍与边界：冻结规范不是禁止变更，而是要求发生变更时显式回到设计或架构阶段。

02

02 · 把父线程保留为协调者

具体问题

如果代理角色既执行又决定自己是否完成，容易缺少独立判断。

采用的处理方式

主线程选择角色、等待结果并决定下一阶段；设计者、实施者、测试者和审查者各自返回结构化结论。

取舍与边界：独立审查无法保证绝对正确，仍要结合实际项目运行、日志和人工操作。

03

03 · 引擎特性通过 Profile 叠加

具体问题

Unity、Godot 与 Unreal 的运行、资源导入和验证入口不同，单一强行统一的工作流容易遗漏引擎边界。

采用的处理方式

保留引擎无关的核心流程，针对各引擎增加检测与验证配置，不把某种引擎的规则误当为所有项目的公理。

取舍与边界：发行包本身不自动修改下游项目，需通过受控安装器和固定版本进行部署。
